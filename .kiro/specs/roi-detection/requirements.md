# 需求文档：ROI 动态检测与跟踪

## 背景

当前 OCR 系统对整张图片进行全量文字检测，在地铁车厢场景中存在以下问题：
- 摄像头晃动或场景变化时，全图检测浪费算力
- 用户只需要识别特定区域（如"下一站：XXX"显示面板），全图检测会返回大量无关文字
- 固定 ROI 坐标无法适应视频流中的运动场景

## 目标

在现有 OCR 系统中增加 **ROI 动态检测与跟踪** 能力，通过颜色检测定位目标区域 + 目标跟踪器持续跟随，实现视频流中对特定区域的实时 OCR 识别。

## 需求列表

### F1 - 颜色检测定位 ROI

**优先级：** P0

| 编号 | 需求描述 |
|------|---------|
| F1.1 | 系统应支持通过 HSV 颜色空间筛选目标区域的特征颜色（红色顶栏） |
| F1.2 | 颜色检测参数（HSV 范围、最小面积、膨胀核大小）应可通过配置文件调节 |
| F1.3 | 颜色检测应输出目标区域的外接矩形坐标 (x, y, w, h) |
| F1.4 | 应支持对检测到的区域进行扩展（padding），避免裁剪过紧导致文字丢失 |
| F1.5 | 颜色检测失败时（目标不在画面中），系统应跳过当前帧并保持上一次的跟踪状态 |

### F2 - 目标跟踪

**优先级：** P0

| 编号 | 需求描述 |
|------|---------|
| F2.1 | 系统应使用 OpenCV 跟踪器（CSRT/KCF）对颜色检测到的目标区域进行帧间跟踪 |
| F2.2 | 跟踪应在每帧连续执行，避免每帧都做颜色检测的性能开销 |
| F2.3 | 应支持可配置的重新检测间隔（如每 N 帧重新做一次颜色检测修正位置） |
| F2.4 | 跟踪器丢失目标时（跟踪失败），应自动回退到颜色检测模式重新定位 |
| F2.5 | 跟踪结果应输出当前帧的目标区域坐标，供后续 OCR 裁剪使用 |

### F3 - ROI 裁剪与 OCR

**优先级：** P0

| 编号 | 需求描述 |
|------|---------|
| F3.1 | 系统应根据跟踪/检测结果裁剪出 ROI 区域图像 |
| F3.2 | 裁剪后的 ROI 图像应送入现有的 TextDetector + TextRecognizer 进行 OCR |
| F3.3 | OCR 结果应包含 ROI 区域的坐标信息和识别文字 |
| F3.4 | 应支持仅输出 ROI 区域内的文字，过滤掉 ROI 之外的检测结果 |

### F4 - 流式处理集成

**优先级：** P0

| 编号 | 需求描述 |
|------|---------|
| F4.1 | ROI 检测与跟踪模块应能无缝集成到现有的 StreamProcessor 视频流处理流程中 |
| F4.2 | 每帧处理应包含：颜色/跟踪定位 → ROI 裁剪 → OCR 识别 → 输出结果 |
| F4.3 | 系统应支持在配置中启用/禁用 ROI 模式（启用时只处理 ROI，禁用时全图检测） |
| F4.4 | ROI 模式下应输出目标区域的可视化标注（在原图上画出跟踪框） |

### F5 - 配置管理

**优先级：** P1

| 编号 | 需求描述 |
|------|---------|
| F5.1 | 颜色检测的 HSV 范围应在 config.yaml 中可配置 |
| F5.2 | 跟踪器类型（CSRT/KCF）、重新检测间隔应在配置中可指定 |
| F5.3 | ROI padding 大小、最小目标面积等过滤参数应在配置中可调节 |
| F5.4 | 配置应提供合理的默认值，适用于地铁"下一站"显示面板场景 |

### F6 - 异常处理与鲁棒性

**优先级：** P1

| 编号 | 需求描述 |
|------|---------|
| F6.1 | 目标完全离开画面时，系统应优雅处理（不崩溃，输出空结果或提示） |
| F6.2 | 光照变化导致颜色偏移时，HSV 参数应有一定容错范围 |
| F6.3 | 多个相似颜色区域同时出现时，应选择面积最大或最接近上一帧位置的区域 |
| F6.4 | 跟踪失败日志应记录，便于调试和参数调优 |

### F7 - 输出目录与日志管理

**优先级：** P0

| 编号 | 需求描述 |
|------|---------|
| F7.1 | 日志文件应统一保存到 `logs/` 目录下，按日期自动归档（如 `logs/2026-05-26.log`） |
| F7.2 | 检测结果（可视化图片、JSON 等）应保存到 `res/` 目录下 |
| F7.3 | `res/` 下每次运行应创建独立子文件夹，命名格式：`{时间戳}_{检测类别}`（如 `20260526_153012_roi_detect`） |
| F7.4 | 每次运行的子文件夹内应包含：可视化标注图片、OCR 结果 JSON、ROI 裁剪图片（可选） |
| F7.5 | 当 `save_result: false` 时，不创建 `res/` 子文件夹，仅输出到控制台 |
| F7.6 | 日志级别（DEBUG/INFO/WARNING/ERROR）应在 config.yaml 中可配置 |

**目录结构示例：**

```
project/
├── logs/
│   ├── 2026-05-26.log
│   └── 2026-05-27.log
├── res/
│   ├── 20260526_153012_roi_detect/
│   │   ├── annotated_0001.jpg      # 可视化标注图
│   │   ├── annotated_0002.jpg
│   │   ├── ocr_result.json         # OCR 结果 JSON
│   │   └── roi_crop/               # ROI 裁剪图（可选）
│   │       ├── roi_0001.jpg
│   │       └── roi_0002.jpg
│   └── 20260526_160455_full_detect/
│       ├── annotated_0001.jpg
│       └── ocr_result.json
└── config/
    └── config.yaml
```

## 非功能需求

| 编号 | 需求描述 | 指标 |
|------|---------|------|
| NF1 | 颜色检测延迟 | 单帧 < 10ms |
| NF2 | 跟踪器更新延迟 | 单帧 < 5ms |
| NF3 | 总帧处理 FPS | ≥ 15 FPS（1080p） |
| NF4 | GPU 显存增量 | < 100MB |
| NF5 | 代码改动应向后兼容 | 不启用 ROI 模式时，现有全图检测功能不受影响 |

## 各输入模式下的 ROI 行为

| 模式 | ROI 检测方式 | 说明 |
|------|-------------|------|
| 单张图片 | 仅颜色检测 | 无帧间概念，单次颜色检测定位 ROI → 裁剪 → OCR |
| 视频文件 | 颜色检测 + 跟踪 | 逐帧处理，跟踪器帧间跟随，每 N 帧重新检测修正 |
| 数据流 | 颜色检测 + 跟踪 | 同视频文件，连续流式处理 |

## 场景示例

**单张图片识别"下一站"：**

```
1. 加载图片
2. 颜色检测找到红色顶栏区域 → 裁剪 ROI
3. ROI 送 OCR 识别 → 输出结果
```

**视频/流识别"下一站"：**

```
1. 第 0 帧：颜色检测找到红色顶栏区域 → 初始化跟踪器
2. 第 1-29 帧：跟踪器跟随目标 → 裁剪 ROI → OCR 识别
3. 第 30 帧：重新颜色检测修正位置 → 重新初始化跟踪器
4. ... 循环
5. 目标离开画面：跟踪失败 → 输出空结果 → 等待目标重新出现
```

## 技术约束

- 依赖 OpenCV 的 `cv2.TrackerCSRT_create()` 或 `cv2.TrackerKCF_create()`
- 颜色检测基于 OpenCV HSV 颜色空间转换
- 不引入新的深度学习模型，不增加额外模型文件
- 与现有 PaddleOCR 检测/识别流程解耦，通过裁剪 ROI 图像复用现有接口
